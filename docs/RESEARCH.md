# 留底 Liudi：需求与开源参考记录

访问日期：**2026-09-26**。

本次调研用于选择一个能独立完成并公开维护的小型产品方向，范围限于公开资料、官方文件及开源项目说明。没有访问私人用户数据，没有开展用户访谈，也没有验证付费意愿、市场规模或产品效果。

## 结论

选择消费退款、维修和售后材料整理作为首版方向。它具备具体、可复现的任务：将交易信息、诉求、沟通过程和原始附件整理在同一个事项下，并提供打印、备份和恢复能力。

需求背景有公开证据，产品价值仍需真实试用验证。留底不是首个本地材料整理工具；本地保存、时间线、文件摘要和 ZIP 导出均已有开源实现。项目的取舍是纯前端、无账号、手工可完成、聚焦普通消费者，并重视备份可恢复性。

## 三个方向的比较

| 方向             | 可解决的具体问题                       | 首版难点                                                   | 决策                           |
| ---------------- | -------------------------------------- | ---------------------------------------------------------- | ------------------------------ |
| 消费售后材料整理 | 材料分散、经过难回忆、每次跟进重复整理 | 原始附件保存、导出完整性、恢复可靠性、避免混淆法律效力     | 选择，先限于消费退款与维修售后 |
| 本地求职投递跟踪 | 忘记投递进度、联系人和面试安排         | 普通表格也能完成部分任务；自动导入会增加平台适配成本       | 暂不开发，已有本地与自托管参考 |
| 本地续费到期提醒 | 忘记续费日期、重复订阅和费用分散       | 纯前端应用关闭后的可靠提醒受限；通知服务增加部署和维护成本 | 暂不开发，已有完整自托管产品   |

这是基于实现范围和公开资料的产品判断，不是市场排名。没有证据表明其他两个方向没有价值。

## 与有据的对照

有据是本次发现的直接参考，不能把其已有能力包装为留底独创。

| 方面     | 有据 README 所述                                   | 留底首版设计                                 |
| -------- | -------------------------------------------------- | -------------------------------------------- |
| 场景     | 网购商品质量、破损、描述不符及退款处理             | 消费退款、维修和售后往返记录                 |
| 本地数据 | IndexedDB 与 OPFS                                  | IndexedDB，纯前端业务流程                    |
| 核心流程 | 材料分类、正式事实确认、时间线、规则缺口、事实陈述 | 事项、诉求、手工时间线、原始附件、自设跟进日 |
| 文件摘要 | SHA-256                                            | SHA-256，用于内容一致性核对                  |
| 导出     | PDF、CSV、离线 HTML 索引与附件 ZIP                 | 单事项 ZIP 备份、导入为副本、可打印 HTML     |
| AI       | 可选 BYOK 与无状态 Fastify 转发                    | 首版不接入 AI、OCR 或模型服务                |
| 部署结构 | Vue/PWA 与 Fastify API                             | React/TypeScript 静态前端与 PWA              |

“可重新导入的备份”是留底强调的验收目标；本次没有全面检查有据代码，不能据此声称竞品缺少恢复能力。React 与 Vue 等技术差异也不自动构成用户价值。

## 从证据推导出的设计要求

1. **事实和诉求分开记录。** 官方资料要求具体请求与事实依据，因此事项需要清晰说明交易、问题和用户希望如何处理；软件不替用户决定诉求。
2. **原件与整理结果同时保留。** 时间线和打印稿帮助阅读，原始附件承载用户实际提供的材料；不能只有摘要而没有附件。
3. **保存与恢复优先于智能功能。** 本地应用没有远程副本，备份导出成功、备份能够恢复，都应经过验证。
4. **错误必须可见。** 存储失败、损坏备份、缺失附件和摘要不匹配时，不得静默跳过或显示全部成功。
5. **不自动填补未知事实。** 用户记录时间、文件修改时间和导入时间分别表达；没有来源的信息不应被编造成精确事实。

以上是产品设计推论，不是由来源证明的软件效果。

## 首版边界

- 不提供法律判断、赔偿建议、胜诉预测或法定期限计算。
- 自设跟进日是用户的个人计划；不承诺关闭应用后的后台推送。
- SHA-256 只能用于内容一致性检查，不提供真实性认证、可信时间戳、公证或司法证据效力保证。
- 不抓取聊天平台，不自动投诉或公开评价商家，不默认上传业务数据。
- 不要求为了试用提交真实订单、聊天、手机号或地址；演示与测试使用虚构资料。
- 独立编写产品代码。公开项目的许可按访问当日元数据记录；本次没有复制或改编其代码、品牌或素材。

## 仍需验证的问题

- 消费者是否愿意在事项发生时手动记录，而不是等到需要投诉才集中整理？
- 用户能否在手机上独立完成 ZIP 导出、找到下载文件并恢复副本？
- 相比相册、文件夹和备忘录，整理时间和遗漏数量是否实际下降？
- 打印材料索引是否便于第三方阅读，而不会误认为经过软件认证？
- 用户会不会把浏览器本地保存误认为永久存储或自动云备份？

试用步骤和初步通过门槛见 [PRODUCT.md](PRODUCT.md)。在完成这些验证前，项目应被描述为具备明确用途的开源首版，而非经过市场验证的成功产品。
