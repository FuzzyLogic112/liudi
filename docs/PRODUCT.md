# 留底 Liudi：首版产品说明

留底帮助消费者把退款、维修和售后沟通中的零散记录，整理成一份可回看、可备份、可打印的材料包。项目采用 React、TypeScript 与 IndexedDB，业务数据保存在当前浏览器；核心流程不依赖账号、AI 服务或远程数据库。

本文定义首版范围与验收要求，不代表所有场景均已通过真实使用验证。测试结果、启动方式和发布信息以仓库实际记录为准。

## 要解决的问题

一笔售后事项可能同时包含订单、付款凭证、问题照片、商家回复和寄修记录。它们分散在相册、聊天应用和下载目录中，用户每次跟进都要重新寻找资料、回忆先后顺序。

留底的目标是缩短“把一件事情说明白”的准备时间：记录自己的诉求，把附件关联到具体事件，按照时间顺序回看，并在需要时带走完整资料。它不判断责任、计算赔偿或预测处理结果。

首批使用场景聚焦消费退款、商品维修和售后沟通。劳动、租房、诉讼等场景需要不同的流程知识，不在首版范围内。

## 目标用户与价值假设

- 正在处理一件或少量售后事项，需要反复向商家说明情况的个人消费者。
- 希望资料留在自己的设备，不愿为临时事项注册新账号的用户。
- 愿意手动记录关键事实，但不想维护文件夹、表格和材料编号的用户。

待验证的假设：以事项为单位整理资料，比用户现有的相册、备忘录和文件夹组合更省事。公开投诉统计支持这一需求背景，但不能证明用户会使用留底，也不能证明软件能提高退款成功率。

## 首版使用流程

1. **建立事项**：填写标题、商家、交易信息、金额和自己的诉求；可设置下一次跟进日期。
2. **记录经过**：按实际发生时间添加时间线条目，说明发生了什么、对方如何回复。未知信息允许留待补充，不自动补造事实。
3. **关联材料**：添加原始附件并关联到相关记录，为附件计算 SHA-256 摘要；避免仅留下截图说明而丢失文件本身。
4. **继续跟进**：回看时间线、更新进展和自设跟进日。跟进日是个人计划，不是系统计算的法定期限。
5. **带走资料**：导出单个事项的 ZIP 备份，包含结构化记录与原始附件；或生成可打印 HTML，供浏览器打印、保存为 PDF。
6. **恢复副本**：重新导入备份并建立独立副本，不覆盖现有事项。导入时核对附件和记录的一致性。

## 范围与取舍

| 首版包含                     | 首版不包含                         |
| ---------------------------- | ---------------------------------- |
| 事项、金额、诉求与自设跟进日 | 法律意见、赔偿计算与法定期限计算   |
| 手工时间线与原始附件         | OCR、聊天平台抓取、自动事实提取    |
| SHA-256 文件内容校验         | 公证、可信时间戳、真实性认证       |
| 单事项 ZIP 备份与副本恢复    | 云端同步、账号体系与多人协作       |
| 可打印 HTML 与浏览器打印     | 自动向平台、商家或行政机关提交资料 |
| PWA 离线使用                 | 关闭应用后保证送达的后台推送       |

选择较小范围，是为了先完成可用的材料整理、导出和恢复闭环。后续功能以真实试用发现的问题决定，不以增加 AI 功能作为默认方向。

## 数据与使用边界

- 数据保存在当前浏览器的 IndexedDB。更换浏览器、设备、访问地址或清除站点数据，不会自动迁移资料；应使用 ZIP 备份和恢复功能。
- PWA 离线使用依赖该设备先成功加载并缓存应用。离线能力不等于云端备份，也不等于浏览器永远保留数据。
- ZIP 备份和打印材料可能包含用户主动录入的姓名、订单、地址或其他个人信息。首版导出不提供加密，用户需要自行选择保管和分享对象。
- SHA-256 用于比较文件字节是否一致。相同摘要不证明材料内容真实，也不能证明材料发生或形成的时间。
- 用户录入的事件时间、文件自身的修改时间和导入时间是不同概念，不应混为一谈。
- 业务数据不因使用应用而主动上传；用户选择导出和分享后，接收方的数据处理不受本应用控制。

## 首版验收重点

| 场景                                           | 应达到的结果                                               |
| ---------------------------------------------- | ---------------------------------------------------------- |
| 新建事项、记录经过、添加附件并刷新             | 已保存的数据仍然存在，附件能够读取                         |
| 浏览器不允许存储或可用空间不足                 | 明确报告失败，不能将未保存内容显示为保存成功               |
| 导出并重新导入单事项备份                       | 建立副本，记录、附件关联和原始文件内容一致，原事项不被覆盖 |
| 备份格式错误、版本不支持、附件缺失或摘要不匹配 | 拒绝不完整恢复并给出原因，不破坏现有资料                   |
| 同名附件、多份相同内容、特殊文件名             | 不因文件名冲突覆盖材料，导出文件路径保持安全               |
| 标题、备注或附件名称包含 HTML 字符             | 页面和打印文档按文本显示，不执行用户内容                   |
| 删除事项或材料                                 | 影响对象清晰，避免误删；存储和界面保持一致                 |
| 手机窄屏与键盘操作                             | 能完成创建、编辑、导出等核心步骤                           |
| 完成首次加载后断网                             | 可打开缓存应用并使用已支持的本地流程                       |

验收不应只证明界面可以打开。尤其需要验证备份恢复，因为本地保存发生丢失时，用户只能依赖自己保管的导出文件。

## 真实试用计划

以下为尚未执行的计划，不是用户验证结果。

**第一轮：6 人、每人约 20 分钟。** 邀请有过退款或维修售后经历的使用者，其中至少两人主要使用手机。提供完全虚构的订单、图片与沟通材料，避免为了试用收集真实订单或聊天记录。

所有人完成同一组任务：建立事项，添加三条时间线和三份附件，修改诉求，设置跟进日，导出 ZIP，删除测试副本，重新导入并找到指定附件。再请参与者展示他们平时会如何整理同一组虚构材料，比较过程中的耗时和遗漏。

只记录经参与者同意的任务完成时间、卡住的位置、是否需要帮助、遗漏的材料和口头反馈。无需收集姓名、联系方式、实际交易资料或应用数据库；不将参与者材料上传到公开 Issue。

**首轮通过门槛：** 至少 5 人无需操作指导完成建立事项和导出；6 人都能恢复测试备份并找到指定附件；没有静默数据丢失。若备份恢复或保存失败提示有问题，先修复再邀请下一轮用户。

**第二轮：7 天自愿使用。** 邀请有实际需求的参与者在自己的设备使用，不要求提交私人材料。结束时询问是否再次打开、是否导出备份、与原有方法相比节省了哪些步骤，以及什么原因使他们停止使用。

“值得继续开发”的信号是用户能够独立完成任务，并愿意在下一件售后事项中继续使用；不是下载量、点赞或单次表示喜欢。若用户认为普通文件夹已足够，应优先调整交互或缩小目标人群，而不是宣称价值已被证明。

## 开源与后续决策

代码独立编写。现有开源项目用于理解用户流程和产品取舍，不复制竞品代码、素材或品牌。项目以仓库实际 LICENSE 为准，研究引用见 [RESEARCH.md](RESEARCH.md)。

后续优先考虑真实使用中反复出现的问题，例如批量整理步骤过多、打印材料难读或手机备份不易找回。只有在核心可靠性达标、用户明确需要且维护成本可控时，才扩大产品范围。
